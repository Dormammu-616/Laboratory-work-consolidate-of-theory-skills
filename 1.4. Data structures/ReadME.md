### Лабораторная №1 - связанные списки
#### Техническое задание
##### Проектирование фильтра для парсера маркетплейсов
**Контекст:** Ты разрабатываешь высоконагруженный парсер (например, для мониторинга Avito или Ozon), который работает в несколько потоков. Каждый поток собирает данные о ценах на товары и сбрасывает их в локальный буфер. Из-за требований к экономии памяти и необходимости быстрой вставки (LIFO) в качестве буфера выбран `std::forward_list`.  
Твоя задача — написать функцию конвейерной обработки этих данных перед их отправкой в базу.

##### Структуры данных
Определи структуру для хранения данных о товаре:
```cpp
struct ProductUpdate
{
	uint64_t product_id;
	double price;    // Напиши конструктор для удобной инициализации
};
```

##### Задачи для реализации:
1. **Инициализация буферов:** Создай два объекта `std::forward_list<ProductUpdate>` (имитация двух потоков парсера). Заполни их моковыми данными, обязательно используя метод `emplace_front` для конструирования объектов без лишнего копирования.
2. **Очистка от мусора:** В процессе парсинга иногда попадаются битые данные. Используй метод класса `remove_if` и лямбда-выражение, чтобы удалить из обоих списков товары с отрицательной или нулевой ценой.
3. **Сортировка:** Отсортируй оба списка по возрастанию `product_id`. Так как это пользовательская структура, тебе нужно будет передать в метод класса `sort()` собственный компаратор (лямбду) или перегрузить оператор `<` для структуры.
4. **Слияние:** Объедини второй список с первым с помощью встроенного метода `merge()`. Убедись, что после этой операции второй список стал пустым, а первый остался отсортированным.
5. **Дедупликация:** При парсинге один и тот же `product_id` мог быть собран несколько раз. Используй метод класса `unique()`, передав туда предикат, который оставит только уникальные ID (допускается оставить любую цену дубликата, например, первую встретившуюся).
6. **Передача владения:** Имитируй отправку данных в сетевой модуль. Создай третий `std::forward_list<ProductUpdate> final_buffer` и с помощью семантики перемещения (`std::move`) перенеси в него все данные из первого списка. Распечатай `final_buffer`, чтобы убедиться в корректности данных, и проверь, что первый список теперь пуст (`empty()`).

##### Требования к коду
- Запрещено использовать функции `std::sort`, `std::reverse`, `std::remove` и `std::unique` из библиотеки `<algorithm>`.
- Обращай внимание на то, чтобы не происходило случайного копирования структур (используй перемещение и `emplace`).
- Все проверки должны выводиться в консоль.

### Лабораторная №2 - стек
#### Техническое задание
**Тема лабораторной:** реализация подсистемы отката пакетных изменений в сервисе обновления карточек товаров маркетплейса с использованием `std::stack`.
**Контекст:**  Есть сервис, который пакетно применяет изменения к карточкам товаров: меняет цену, остаток, статус публикации. Перед применением каждого изменения система должна сохранить действие отката, чтобы при ошибке можно было отменить уже выполненные операции в обратном порядке — это естественная задача для стека.

##### Что нужно реализовать
1. Создать структуру `RollbackAction`, которая описывает одну операцию отката.  Минимальные поля:
	- `product_id`
	- `field_name`
	- `old_value`
	- `new_value`
	- `priority` или `timestamp`
2. Создать стек:
```cpp
	std::stack<RollbackAction, std::deque<RollbackAction>> rollbackStack;
```
3. При “применении” каждого изменения помещать соответствующее действие отката в стек. Для этого нужно использовать:
	- `push()` для готового объекта;
	- `emplace()` хотя бы в одном месте, чтобы закрепить конструирование элемента прямо в контейнере.
4. Смоделировать сбой в середине обработки пакета. После возникновения ошибки программа должна:
	- пока стек не пуст, брать верхний элемент через `top()`;
	- выводить в консоль, какое изменение сейчас откатывается;
	- удалять его через `pop()`.
5. После завершения отката вывести:
	- сколько операций было изначально;
	- сколько операций удалось откатить;
	- пуст ли стек после завершения rollback.

##### Ограничения и требования
- Нельзя вызывать `top()` без проверки `empty()`.
- Нельзя пытаться перебирать `std::stack` циклом по итераторам — у адаптера стека итераторов нет.
- Нельзя “удалять конкретный элемент из середины” — стек допускает работу только с вершиной.
- Нужно показать разницу между `push()` и `emplace()`.
- Нужно использовать `size()`, `empty()`, `top()`, `pop()`, `push()` и `emplace()`.

##### Что именно это закрепляет
Это ТЗ хорошо закрепляет не только базовые операции, но и **мышление через модель данных**: стек нужен не “потому что так сказали”, а потому что откат идет строго в обратном порядке выполнения. Заодно ты на практике увидишь главное ограничение `std::stack`: это адаптер, а не “полноценный контейнер для обхода и выборочного удаления”.

##### Что можно добавить для усложнения
- Реализовать второй стек `appliedStack` или `auditStack`, чтобы временно переносить туда успешно считанные действия перед окончательным логированием.
- Проверить перемещение целого стека через `std::move`, но с важной оговоркой: у перемещенного объекта состояние **валидное, но не обязано быть пустым**, поэтому в ТЗ лучше не требовать проверки “после move исходный стек пуст”.
- Добавить меню из команд: `apply`, `fail`, `rollback`, `show_top`, `show_size`, чтобы сделать лабораторную ближе к консольному mini-service.

##### Готовая формулировка ТЗ
**Техническое задание:**  Разработать консольное приложение на C++, моделирующее подсистему отката пакетных изменений карточек товаров в сервисе интеграции с маркетплейсом. Для хранения операций отката использовать адаптер `std::stack` на основе `std::deque`.
**Функциональные требования:**
- Программа должна сохранять действия отката при каждом успешном “изменении” товара.
- Каждое действие отката должно содержать идентификатор товара, имя изменяемого поля, старое и новое значение.
- При возникновении ошибки программа должна выполнить откат всех уже примененных изменений в порядке LIFO.
- Для работы со стеком должны быть использованы операции `push`, `emplace`, `top`, `pop`, `empty`, `size`.
- Перед обращением к `top()` обязательно должна выполняться проверка `empty()`.
**Нефункциональные требования:**
- В качестве базового контейнера использовать `std::deque`.
- Код должен быть разбит на логические функции: применение изменения, добавление rollback-действия, выполнение отката, вывод состояния стека.
- Все ключевые этапы работы должны сопровождаться понятным консольным логом.
**Комментарий по исправлению конспекта:**
- В оригинальном тексте нужно явно отметить, что `top()` для `std::stack` не делает проверку пустоты.
- Нужно отдельно отметить, что `pop()` не возвращает удаляемый элемент.
- Нужно исправить замечание про “переполнение стека большими объектами”: для `std::stack` проблема обычно не в этом, а в стоимости копирования/перемещения тяжелых объектов и в выборе подходящего базового контейнера.

#### Документация
##### Изучаемая теория
В рамках данной лабораторной работы изучался **контейнер-адаптер `std::stack`** из стандартной библиотеки C++, работающий по принципу **LIFO** (Last-In, First-Out — «последним пришел, первым ушел»). Основное внимание уделялось демонстрации различий между методами `push()` и `emplace()`, корректному паттерну работы с `top()` и `pop()`, а также использованию вспомогательных методов `size()` и `empty()`.
Ключевой особенностью `std::stack` является его **ограниченный интерфейс**: отсутствуют итераторы, индексный доступ и операции с середине контейнера. Все операции (`push`, `pop`, `top`) выполняются за **O(1)** только с вершиной стека. Метод `pop()` возвращает `void` и не извлекает данные — для этого сначала используется `top()`, что требует обязательной проверки `empty()` перед обращением к вершине.
##### Архитектура проекта
Проект реализует **демонстратор возможностей `std::stack`** в контексте моделирования системы отката операций. Архитектура строго разделяет ответственности:
1. **`RollbackAction`** — структура данных для хранения снимков изменений (ID товара, тип поля, старое/новое значения)
2. **`ProductAttribute`** — строго типизированное перечисление для идентификации изменяемых атрибутов
3. **`std::stack<RollbackAction>`** — основное хранилище с гарантированным LIFO-поведением
4. **`LabRunner`** — оркестратор лабораторного сценария с тремя этапами демонстрации
Логика работы: сначала добавляются готовые объекты через `push()`, затем демонстрируется конструирование на месте через `emplace()`, после чего показывается корректный паттерн чтения (`top()`) и удаления (`pop()`) с логированием состояния.
```

   └── enum class ProductAttribute : uint8_t

       └── Конструктор для emplace()
       └── Поля: product_id, field_name, padding, old/new_value

📄 LabRunner.h
   └── class LabRunner
       └── void run_lab_stack()
       └── void print_top_elem_stack()

📄 LabRunner.cpp
   └── #include "RollbackAction.h" 
   └── #include "LabRunner.h"
       └── Этап 1: push() трех готовых объектов

📄 main.cpp  
   └── #include "LabRunner.h"
       └── LabRunner lab;
       └── lab.run_lab_stack();
```

### Лабораторная №3 - очередь
#### Техническое задание: Система обработки заказов маркетплейса
##### 1. Контекст проекта
**Сервис "FastDeliveryHub"** — высоконагруженная система обработки заказов интернет-магазина, интегрированная с тремя основными подсистемами:
1. **Клиентские заказы** поступают от покупателей в строгом порядке времени регистрации и должны обрабатываться точно в том же порядке (принцип FIFO).
2. **VIP-заказы** премиум-клиентов имеют высокий приоритет (1-10 баллов). Критично обрабатывать сначала самые срочные заказы, независимо от времени их поступления.
3. **Складские операции** включают комплектацию товаров, отгрузку и пополнение запасов. Склад работает с обоих концов: комплектовщики загружают товары спереди, погрузчики забирают готовые партии сзади.
**Цель лабораторной работы**: продемонстрировать применение трех типов очередей STL (`std::queue`, `std::priority_queue`, `std::deque`) для решения реальных задач с различными моделями обработки данных.

##### 2. Структура данных
Необходимо определить структуру `OrderTask`, содержащую:
- `order_id` — уникальный идентификатор заказа (тип `uint64_t`)
- `priority` — приоритет обработки (тип `uint8_t`, диапазон 1-10, для VIP-заказов)
- `operation` — тип операции (тип `std::string`) 
- Конструктор для поддержки операции `emplace()`

##### 3. Что необходимо реализовать
1. Инициализация контейнеров. Создать три контейнера для различных типов задач:
	- Обычная очередь клиентских заказов (FIFO)
	- Приоритетная очередь VIP-заказов с пользовательским компаратором
	- Двусторонняя очередь складских операций
	Определить структуру компаратора для приоритетной очереди (>), сортирующего по убыванию приоритета.
2. Наполнение очередей: заполнить каждую очередь четырьмя задачами различного характера:
	- Клиентские заказы (строго по порядку поступления): Добавить четыре задачи в обычную очередь, демонстрируя FIFO-принцип.
	- VIP-заказы (различные приоритеты): Добавить четыре задачи с разными значениями приоритета (от высокого до низкого).
	- Складские операции (смешанная нагрузка): Две задачи добавить в начало очереди и Две задачи добавить в конец очереди.
3. Обработка задач: Обработать по две задачи из каждой очереди с логированием результатов.
	- Клиентские заказы: Извлечь две задачи из начала очереди и обработать их.
	- VIP-заказы: Извлечь две задачи с наивысшим приоритетом.
	- Складские операции: Обработать одну задачу из начала и одну из конца очереди. Формат лога для каждой операции: `[ВРЕМЯ] [ТИП_ОЧЕРЕДИ] Заказ #ID (операция, приоритет) -> Обработан`.
4. **Анализ** состояния очередей: После обработки вывести текущее состояние всех контейнеров. 
	- Количество оставшихся задач в каждой очереди.
	- Первый элемент для обычной и двусторонней очередей.
	- Элемент с максимальным приоритетом для VIP-очереди.
	- Статус пустоты очередей.

##### 4. Ограничения и требования
Обязательные операции (все контейнеры):
- Конструирование объектов на месте (`emplace`).

##### Изучаемая теория
В ходе реализации проекта были закреплены следующие концепции языка C++:
- Контейнеры-адаптеры (Container Adaptors): Понимание разницы между `std::queue` (ограниченный интерфейс) и базовым контейнером `std::deque`.
- Приоритетные очереди: Использование `std::priority_queue` и написание функциональных объектов (functors) для определения логики сортировки.
- Управление памятью и emplace: Понимание механизма _perfect forwarding_. В отличие от `push()`, `emplace()` конструирует объект непосредственно внутри памяти контейнера, избегая лишнего копирования или перемещения.
- Принципы доступа к данным:
    - FIFO (First-In-First-Out): Обычные заказы.
    - Priority Driven: VIP-заказы.
    - Double-Ended: Складские операции (свободный доступ к голове и хвосту). 

##### Архитектура и структура проекта
Проект организован по принципу разделения ответственности:
Ключевые компоненты:
1. Data Layer (`OrderTask`): Низкоуровневая структура (POD-тип) для хранения данных заказа. Вынесена отдельно для обеспечения легкости передачи между модулями.
2. Logic Layer (`LabRunner`): Класс-контроллер, инкапсулирующий логику выполнения лабораторной работы.
    - Метод `run_lab_queue()` выступает в роли входной точки сценария.
3. Comparator Layer: Отдельный функциональный объект (структура с перегруженным `operator()`), который используется `priority_queue` для построения бинарной кучи.

Структура файлов:
- `OrderTask.h`: Объявление структуры и перегрузка операторов вывода.
- `Comparators.h`: Все логические правила сравнения задач.
- `LabRunner.h/cpp`: Реализация сценария тестирования.
- `main.cpp`: Минималистичная точка входа, создающая экземпляр Runner.

### Лабораторная №4 - хэш-таблицы
#### Техническое задание:
##### 1. Контекст проекта
Вы разрабатываете модуль для высоконагруженного API-гейтвея. Модуль "RapidAuth" должен мгновенно проверять токены доступа пользователей. Поскольку обращение к основной базе данных занимает слишком много времени, необходимо реализовать локальный кэш на основе хэш-таблиц.
**Цель лабораторной работы:** реализовать и сравнить две стратегии разрешения коллизий (метод цепочек и открытую адресацию) и интегрировать решение с `std::unordered_map`.

##### 2. Структура данных
Определите структуру `UserSession`:
- `session_token` — уникальный ключ (тип `string`).
- `user_id` — идентификатор пользователя (тип `uint64_t`).
- `access_level` — уровень доступа (тип `int`).
- Реализовать конструктор для работы с `emplace`.

##### 3. Что необходимо реализовать
1. Собственная реализация (Метод цепочек). Создать класс `SessionCacheChaining`:
	- Основа: `std::vector<std::list<UserSession>>`.   
	- Хэш-функция: Реализовать полиномиальный хэш вручную (как в примере `simpleHash`) .
	- Методы:
	    - `emplace(const UserSession data)`: с проверкой на `load_factor`. Если значение >0.75, вызвать `rehash()`.
	    - `erase(const std::string& session)`: нахождение элемента через `std::find_if`, его физическое удаление из `std::list` и обязательный декремент общего счетчика элементов. Возвращает количество удаленных элементов (`1` или `0`).
	    - `rehash()`: увеличить размер таблицы до ближайшего простого числа (или просто удвоить) и перераспределить элементы .
	    - `find()`: возвращает указатель на сессию или `nullptr`.
2. Собственная реализация (Открытая адресация). Создать класс `SessionCacheOpenAddr`:
	- Основа: `std::vector<Entry>`, где `Entry` содержит:
		- `user_data` — объект типа `UserSession`.
		- `user_state` — перечисление `State` (`EMPTY`, `OCCUPIED`, `DELETED`).
		- `padding[4]` — выравнивающий массив (`uint8_t`).
	- Методы:
		- `emplace(const UserSession data)`: вставка с проверкой `load_factor()`. Применяется стратегия ленивой вставки (выбирается первая встреченная ячейка со статусом `DELETED` или `EMPTY`). Дубликаты игнорируются.
		- `erase(const std::string& session)`: поиск элемента через `find_entry`. В случае успеха ячейка помечается как `DELETED`, строка токена очищается (`.clear()`), а счетчик `occupied_count` не уменьшается (стратегия «грязного» load_factor). Возвращает `1` или `0`.
		- `rehash()`: увеличение емкости вектора в 2 раза. В процессе рехаша все ячейки со статусом `DELETED` полностью очищаются (счетчик `occupied_count` пересчитывается с нуля), а валидные сессии перемещаются с помощью `std::move`.
	- Удаление: При удалении помечать ячейку как DELETED, чтобы не разрывать цепочки поиска.
3. Работа с STL. Продемонстрировать использование стандартных контейнеров для той же задачи
	- Интеграция со стандартным контейнером `std::unordered_map<std::string, UserSession>` для формирования эталонных метрик.

##### 4. Сценарии тестирования и критерии успешности
Тестирование состоит из трех последовательных фаз на объеме данных 10 000 элементов:
1. **Фаза 1: Массовое первичное заполнение.** Измерение скорости заполнения пустых таблиц, фиксация пикового потребления памяти (с учетом `capacity` векторов) и стартового Load Factor.
2. **Фаза 2: Насыщение дубликатами.** Попытка повторного добавления 25% (2500 элементов) случайно выбранных существующих сессий.
    - *Критерий успеха*: Время операции должно быть минимальным, а память и Load Factor всех трех контейнеров должны остаться строго неизменными, что доказывает корректность защиты от дубликатов.
3. **Фаза 3: Частичное удаление.** Удаление тех же самых 25% элементов из таблиц.
    - *Критерий успеха:*
	    * В `Chaining` и `STL` память и Load Factor должны снизиться (происходит физическое освобождение узлов).
	    * В `OpenAddr` память должна остаться неизменной, Load Factor не должен уменьшиться (Tombstones учитываются как занятые ячейки), а время удаления должно быть минимальным (~1 ms) из-за отсутствия обращений к аллокатору ОС.

#### Документация
##### Изучаемая теория
В ходе реализации проекта были подробно изучены и закреплены следующие концепции хэширования, структуры данных и языка C++:
- Устройство хэш-таблиц и разрешение коллизий: Изучены фундаментальные принципы организации ассоциативной памяти. Освоены две полярные стратегии разрешения коллизий — метод цепочек (закрытое адресование, где коллизии разрешаются созданием динамических связанных списков) и открытая адресация (открытое адресование, где поиск свободных мест происходит внутри единого фиксированного массива).
- Линейное пробирование и ленивое удаление: На примере открытой адресации освоен алгоритм кольцевого линейного зондирования. Изучена концепция маркеров удаления (`DELETED` / Tombstones) в ячейках таблицы. Данный механизм необходим для сохранения непрерывности цепочек пробирования при поиске элементов, стоящих в массиве «за» удаленным элементом.
- Хэш-функции и полиномиальный хэш: Изучена математическая модель построения хэш-кодов для строковых ключей. Реализован кастомный алгоритм полиномиального хэширования, преобразующий строки токенов в индексы массива, и проведено его сопоставление со стандартным системным хэшем.
- Стандартный хэш из STL (`std::unordered_map`): Изучена архитектура эталонного контейнера стандартной библиотеки C++. Контейнер `std::unordered_map` рассмотрен как промышленный baseline-ориентир для анализа производительности, эффективности автоматического перестроения (`rehash`) и стратегий управления памятью.

##### Архитектура и структура проекта
Проект строго разграничен на слои хранения данных, алгоритмическую часть и слой проведения бенчмарка. Ключевые компоненты:
- **Data Layer (`UserSession`, `Entry`):** Низкоуровневые структуры данных. `UserSession` инкапсулирует в себе токен-ключ и информацию о пользователе, являясь базовым элементом для метода цепочек. Структура `Entry` расширяет сессию флагами состояний ячейки, формируя базис для открытой адресации.
- **Algorithm Layer (`SessionCacheChaining`, `SessionCacheOpenAddr`):** Самостоятельные классы хэш-таблиц, изолирующие внутри себя индивидуальную математику индексации, логику защиты от дубликатов, алгоритмы удаления `erase` и стратегии увеличения емкости `rehash`.
- **Benchmark Layer (`LabRunner`):** Класс-контроллер, управляющий жизненным циклом эксперимента. Он отвечает за генерацию воспроизводимых случайных данных (через `std::mt19937`), выборку подмножеств с помощью `std::sample`, замер времени монотонных часов и вызов процедур сбора метрик памяти.

Структура файлов:
- **UserSession.h** (и сопутствующий `.cpp` при наличии): Содержит объявление структуры `UserSession` с полями данных сессии (`session_token`, `user_id`, `access_level`) и конструкторами, используемыми в `SessionCacheChaining`.
- **Entry.h** (или в составе файлов сущностей): Хранит определение структуры ячейки `Entry` (содержит `UserSession`, перечисление состояний `State` и массив `padding`) для нужд `SessionCacheOpenAddr`.
- **SessionCacheChaining.h:** Полное объявление и реализация хэш-таблицы на основе метода цепочек (`std::vector<std::list<UserSession>>`).
- **SessionCacheOpenAddr.h:** Полное объявление и реализация хэш-таблицы на основе открытой адресации и линейного зондирования (`std::vector<Entry>`).
- **LabRunner.h / LabRunner.cpp:** Описание и реализация сценария тестирования, шаблонного движка выполнения операций `run_operation_data_in_hash`, вычисления объемов памяти контейнеров и форматированного вывода таблицы метрик.
- **main.cpp:** Минималистичная точка входа в программу, которая инициализирует объект `LabRunner` и запускает последовательное выполнение фаз лабораторной работы.
