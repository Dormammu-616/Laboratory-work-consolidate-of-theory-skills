Данный цикл из трех лабораторных работ направлен на глубокое практическое освоение Принципа инверсии зависимостей (Dependency Inversion Principle - DIP) в рамках современной разработки на C++. В процессе выполнения заданий осуществляется архитектурный переход от монолитного, жестко связанного legacy-кода к гибкой системе, где высокоуровневая бизнес-логика полностью изолирована от нестабильных низкоуровневых деталей реализации. Практическая проработка охватывает применение паттерна Dependency Injection, грамотное распределение физического владения абстракциями между пакетами и формирование единой точки сборки зависимостей (Composition Root), что закладывает надежный фундамент для масштабирования и изолированного модульного тестирования.
## Лабораторная работа №1: Инверсия зависимостей в финансовом ядре: изоляция бизнес-логики от инфраструктуры (Isolating business logic from infrastructure)
### Техническое задание
#### Контекст и Цель работы
- *Контекст*: При традиционном инженерном подходе изменения в механизмах доставки (например, смена SQL-диалекта, обновление драйверов или смена форматов данных) каскадируют вверх по иерархии, вынуждая разработчиков переписывать и перетестировать саму бизнес-логику.
- *Цель работы*: Развернуть стрелки зависимостей, применив DIP. Необходимо спроектировать систему оценки кредитоспособности таким образом, чтобы нестабильные детали реализации зависели от стабильных контрактов ядра, а само ядро можно было тестировать в полной изоляции.
#### Архитектурные требования (Контракты и Абстракции)
- Создать пространство имен `namespace BusinessLogic`, которое будет полностью независимым от деталей реализации (не должно ничего знать о базах данных или сети).
- Внутри `BusinessLogic` определить чистый абстрактный интерфейс `ICustomerRepository` со следующими методами:
    - `virtual ~ICustomerRepository() = default;` — обязательный виртуальный деструктор.
    - `[[nodiscard]] virtual int getCreditScore(std::string_view customerId) const = 0;` — метод получения кредитного рейтинга, выраженный на языке бизнес-логики. Использование `std::string_view` обязательно согласно стандартам C++17 для избежания лишних аллокаций.
#### Детали реализации (Конкретные компоненты)
- Создать пространство имен `namespace Infrastructure` для размещения низкоуровневых компонентов.
- Реализовать класс `PostgreSQLCustomerRepository`, публично наследующий `BusinessLogic::ICustomerRepository`.
    - Реализовать метод: `[[nodiscard]] int getCreditScore(std::string_view customerId) const override;`
    - Логика метода: вывести в консоль имитацию обращения к БД (например, `"[PostgreSQLCustomerRepository] Открытие соединения с БД. Поиск рейтинга для ID: ... "`) и вернуть фиксированное значение `750`.
- Реализовать класс `MockCustomerRepository`, публично наследующий `BusinessLogic::ICustomerRepository`.
    - Реализовать метод: `[[nodiscard]] int getCreditScore(std::string_view customerId) const override;`
    - Логика метода: вывести в консоль имитацию работы быстрой in-memory заглушки (например, `"[MockCustomerRepository] Чтение рейтинга из кэша памяти для ID: ... "`) и вернуть фиксированное значение `400`.
- Направление зависимостей (и директив `#include`) должно идти строго от `Infrastructure` к `BusinessLogic`.
#### Изолированная бизнес-логика
- Внутри `BusinessLogic` реализовать класс `LoanCalculator` (ядро системы).
- Класс должен содержать приватное поле: `std::shared_ptr<ICustomerRepository> m_repository;`
- Конструктор: `explicit LoanCalculator(std::shared_ptr<ICustomerRepository> repository);` — осуществляет Constructor Injection. Класс не должен использовать `new` для создания репозиториев внутри себя.
- Бизнес-метод: `void assessLoanApplication(std::string_view customerId) const;`
    - Логика метода: запросить рейтинг через `m_repository->getCreditScore(customerId)`. Если рейтинг больше или равен `600`, вывести сообщение `"[LoanCalculator] Рейтинг: <score>. Кредит одобрен."`. Иначе — `"[LoanCalculator] Рейтинг: <score>. В кредите отказано."`.
#### Точка сборки (main.cpp)
- Использовать `main.cpp` как корень композиции (Composition Root).
- В `main()`:
    1. Вывести стартовое сообщение: `std::cout << "*** Start laboratory #1 - Isolating business logic from infrastructure ***\n\n";`
    2. Использовать `std::make_shared` для создания объекта `PostgreSQLCustomerRepository`.
    3. Внедрить его в `LoanCalculator` и вызвать `assessLoanApplication("ID-101")`.
    4. Продемонстрировать подмену контекста: создать `MockCustomerRepository`, передать его в новый экземпляр `LoanCalculator` и вызвать тот же метод `assessLoanApplication("ID-101")`, доказав, что ядро работает корректно с другой инфраструктурой.
#### Критерии профессионального выполнения
- [x] Compilation Firewall: В файлах пространства `BusinessLogic` категорически запрещено писать `#include` на файлы из `Infrastructure`.
- [x] Const Correctness: Все методы, не меняющие состояние объектов, должны быть помечены как `const`.
- [x] Строгая типизация и память: Использование `override` для реализации контрактов, `[[nodiscard]]` для методов возврата, `explicit` для конструктора ядра и умных указателей `std::shared_ptr` для передачи зависимости.

- Архитектурный паттерн: Dependency Injection (Внедрение зависимостей через конструктор) и Composition Root.

Архитектура проекта строго разделена на два изолированных пакета (пространства имен), где стрелка зависимости исходного кода направлена строго от низкоуровневых деталей к высокоуровневым абстракциям.
- Уровень Бизнес-Логики (`namespace BusinessLogic`):
    - `ICustomerRepository` (Абстракция): Чистый виртуальный интерфейс. Логически и физически принадлежит ядру приложения. Диктует инфраструктуре правила предоставления данных (в данном случае — кредитного рейтинга).

- Уровень Инфраструктуры (`namespace Infrastructure`):
    - `PostgreSQLCustomerRepository`: Конкретная деталь реализации. Наследует (подчиняется) контракт `BusinessLogic::ICustomerRepository` и имитирует тяжелую работу с реальной базой данных.
    - `MockCustomerRepository`: Альтернативная деталь реализации. Также наследует интерфейс ядра, но предоставляет in-memory заглушку для мгновенного модульного тестирования.
- Точка сборки (Composition Root):
    - `main.cpp`: Единственное место в проекте, которое обладает знанием обо всех компонентах системы. Именно здесь нарушается изоляция (подключаются файлы из обоих namespace), чтобы создать объекты инфраструктуры и "внедрить" их в ядро бизнес-логики.

## Лабораторная работа №2: "Защита архитектурных границ: Паттерн Адаптер для интеграции сторонних библиотек" (AdapterDIP)
### Техническое задание
#### Контекст и Цель работы
- *Контекст*: В проекте появилась необходимость отправлять уведомления пользователям через популярный сторонний сервис SMS-рассылок (например, Twilio). Библиотека вендора поставляется "как есть" (как конкретный класс). Если мы вызовем ее методы напрямую из ядра, мы нарушим DIP и намертво привяжем нашу бизнес-логику к конкретному внешнему провайдеру.
- *Цель*: Использовать структурный паттерн проектирования "Адаптер объекта" (Object Adapter) для защиты ядра приложения. Заставить несовместимую стороннюю библиотеку "подчиниться" правилам нашей бизнес-логики без изменения её исходного кода.
#### Архитектурные требования (Контракты и Абстракции)
- В пространстве имен `namespace BusinessLogic` создать чистый абстрактный интерфейс `INotifier`.
- Методы контракта:
    - `virtual ~INotifier() = default;`  
    - `virtual void send_notification(std::string_view message) const = 0;` — метод, говорящий исключительно на языке бизнеса. Обрати внимание: он не принимает номер телефона, так как ядру (в данном контексте) важен только текст сообщения.
#### Детали реализации (Конкретные компоненты)
- Создать пространство имен `namespace ExternalVendor` (симуляция чужой закрытой библиотеки).
    - В нем реализовать класс `TwilioApi`. Внимание: этот класс _не наследуется_ ни от каких наших интерфейсов!
    - Реализовать метод: `void send_sms(std::string_view phone_number, std::string_view text) const;`.
    - Логика метода: имитация работы сети `std::cout << "[ExternalVendor::TwilioApi] Sending SMS to '" << phone_number << "': " << text << "\n";`
- Создать пространство имен `namespace Infrastructure` для нашего связующего кода.
    - Реализовать класс `TwilioNotifierAdapter`, публично наследующий `BusinessLogic::INotifier`.
    - Адаптер должен принимать в конструктор объект (или указатель) `ExternalVendor::TwilioApi`, а также строку с номером телефона (ведь интерфейсу ядра номер не передается). Использовать композицию (сохранить API и номер как приватные поля адаптера).
    - Реализовать метод `send_notification(...) override`, который внутри себя будет вызывать `m_twilio_api->send_sms(m_phone, message)`.
#### Изолированная бизнес-логика
- Внутри `namespace BusinessLogic` реализовать класс `UserManager` (наше ядро).
- Класс принимает зависимость через конструктор: `explicit UserManager(std::shared_ptr<INotifier> notifier)`.
- Бизнес-метод: `void register_user(std::string_view username) const;`.
    - Логика: вывести сообщение `"[BusinessLogic::UserManager] User '<username>' successfully registered.\n"`.
    - Сразу после этого вызвать: `m_notifier->send_notification("Welcome to our platform!");`.
#### Точка сборки (main.cpp)
1. Вывести сообщение: `std::cout << "*** Start laboratory #2 - Protecting boundaries with Adapter ***\n\n";`
2. Создать экземпляр "чужой" библиотеки `ExternalVendor::TwilioApi`.
3. Создать наш `Infrastructure::TwilioNotifierAdapter`, передав в него API и какой-нибудь тестовый номер телефона (например, `"+1-555-0199"`).
4. Создать ядро `BusinessLogic::UserManager`, внедрив в него адаптер (приведенный к `std::shared_ptr<INotifier>`).
5. Вызвать метод `register_user("Alice")`.
#### Критерии профессионального выполнения
- [x] Strict Dependencies: Файлы в `BusinessLogic` не имеют права подключать (include) файлы из `ExternalVendor` или `Infrastructure`. Компилятор должен ругаться, если ядро попытается узнать о существовании Twilio.
- [x] Composition over Inheritance: Адаптер должен использовать _композицию_ (содержать экземпляр стороннего класса внутри себя), а не множественное наследование, чтобы скрыть лишние методы API от ядра.
- [x] One class = One file: Продолжаем соблюдать правило: для `INotifier`, `TwilioApi`, `TwilioNotifierAdapter` и `UserManager` создаются свои собственные заголовочные (и, где нужно, cpp) файлы.
### Документация
#### Требования и стек технологий:
- Стандарт языка: C++17.
- Среда разработки и компилятор: Visual Studio (MSVC) / GCC 9+ / Clang 7+.
- Требования к коду: Использование структурного паттерна Object Adapter (Адаптер объекта) на основе композиции (`Composition over Inheritance`), строгая инкапсуляция стороннего кода, передача строк через `std::string_view` для оптимизации производительности, владение строками внутри классов через `std::string` и перемещение (`std::move`).
- Архитектурный паттерн: Dependency Inversion Principle в связке с паттерном Adapter для защиты от Vendor Lock-in (привязки к поставщику).
#### Логическая структура и взаимодействие классов:
Архитектура проекта демонстрирует изоляцию бизнес-логики от внешних несовместимых зависимостей путем возведения промежуточного слоя (Адаптера).
- Уровень Бизнес-Логики (`namespace BusinessLogic`):
    - `INotifier` (Абстракция): Абстрактный контракт, выражающий потребность ядра в отправке уведомлений (принимает только текст сообщения).
    - `UserManager` (Ядро): Класс управления пользователями. Ничего не знает о каналах доставки (SMS, Email, Push) и конкретных провайдерах. Зависит исключительно от `INotifier`.
- Уровень Сторонней библиотеки (`namespace ExternalVendor`):
    - `TwilioApi`: Имитация закрытого, немодифицируемого класса стороннего поставщика (Third-party library). Обладает собственным интерфейсом (`send_sms`), который несовместим с требованиями нашего ядра и требует дополнительных данных (номер телефона).
- Уровень Инфраструктуры (`namespace Infrastructure`):
    - `TwilioNotifierAdapter`: Класс-переводчик. С одной стороны, он публично реализует контракт `BusinessLogic::INotifier`, чтобы ядро могло с ним работать. С другой стороны, он инкапсулирует в себе (через композицию) указатель на `ExternalVendor::TwilioApi` и инфраструктурные настройки (номер телефона), переводя вызовы ядра в понятный для сторонней библиотеки формат.
- Точка сборки (Composition Root):
    - `main.cpp`: Инициализирует стороннее API, оборачивает его в Адаптер вместе с конфигурационными данными (телефонным номером) и внедряет готовый Адаптер (путем неявного приведения к `INotifier`) в `UserManager`.
#### Пример работы программы:
```cpp

[Infrastructure::TwilioNotifierAdapter] Sending...
[ExternalVendor::TwilioApi] Sending SMS to '+1-555-555-0199': Welcome to our platform!.
```
## Лабораторная работа №3: «Динамическая подмена поведения: Инверсия зависимостей и паттерн Стратегия» (DynamicStrategyDIP)
### Техническое задание
- *Контекст*: В современных E-commerce системах способы оплаты (карты, криптовалюта, электронные кошельки) регулярно добавляются и меняются. Если ядро системы (процесс оформления заказа) будет само решать, как проводить оплату через ветвления `if / switch`, оно быстро превратится в неподдерживаемый монолит, жестко связанный со всеми платежными шлюзами.
- *Цель работы:* Применить паттерн "Стратегия" на базе DIP. Спроектировать ядро оформления заказов так, чтобы оно зависело только от абстрактного контракта оплаты. Научиться изменять поведение ядра "на лету" (в Runtime), передавая ему новые реализации контракта без пересоздания самого объекта бизнес-логики.
#### Архитектурные требования (Контракты и Абстракции)
- В пространстве имен `namespace BusinessLogic` создать файл чистого интерфейса `IPaymentMethod.hpp`.
- Контракт должен содержать:
    - `virtual ~IPaymentMethod() = default;`
    - `virtual void process_payment(double amount) const = 0;` — абстрактный алгоритм проведения платежа.
#### Детали реализации (Конкретные компоненты)
- В новом пространстве имен `namespace PaymentGateways` (которое будет символизировать внешние плагины оплат) создать два класса-стратегии:
    1. `CreditCardPayment`: публично наследует `IPaymentMethod`. В реализации метода выводит: `"[PaymentGateways::CreditCard] Processing credit card payment: $<amount>.\n"`
    2. `CryptoPayment`: публично наследует `IPaymentMethod`. В реализации метода выводит: `"[PaymentGateways::Crypto] Processing cryptocurrency payment: $<amount>.\n"`
- Напоминание: Для каждого класса создаем свой отдельный `.hpp` (и `.cpp`, если реализация не inline). Эти классы обязаны подключать контракт ядра.
#### Изолированная бизнес-логика
- Внутри `namespace BusinessLogic` реализовать класс `OrderCheckout` (ядро оформления заказа).
- Класс должен хранить текущую стратегию оплаты: `std::shared_ptr<IPaymentMethod> m_payment_method;`.
- Конструктор: `explicit OrderCheckout(std::shared_ptr<IPaymentMethod> method);`.
- *Динамическая подмена (Setter Injection)*: Метод `void change_payment_method(std::shared_ptr<IPaymentMethod> new_method);` — именно он позволяет изменить алгоритм в любой момент. Убедись, что используешь семантику перемещения (`std::move`) при присваивании нового указателя.
- Бизнес-метод: `void checkout(double amount) const;`. Метод должен выводить `"[BusinessLogic::OrderCheckout] Initiating checkout process...\n"` и затем делегировать выполнение операции текущей стратегии: `m_payment_method->process_payment(amount);`.
#### Точка сборки (main.cpp)
1. Вывести сообщение: `std::cout << "*** Start laboratory #3 - Dynamic behavior with Strategy Pattern ***\n\n";`
2. Создать объекты обеих стратегий оплат (`std::make_shared`).
3. Создать ядро `BusinessLogic::OrderCheckout`, передав в конструктор стратегию банковской карты.
4. Совершить покупку: вызвать `checkout(150.50)`.
5. Смена поведения: Вызвать `change_payment_method(...)` у объекта чекаута, передав туда стратегию криптовалюты.
6. Совершить вторую покупку: вызвать `checkout(99.99)`.
#### Критерии профессионального выполнения
- [x] Compilation Firewall: Ядро (`OrderCheckout`) и контракт (`IPaymentMethod`) не должны содержать ни одного `#include` на классы из пакета `PaymentGateways`.
- [x] Safety (Безопасность): В настоящем коде перед вызовом `m_payment_method->process_payment` внутри `checkout` стоит проверить указатель на валидность (`if (m_payment_method) { ... } else { /* error */ }`), чтобы избежать "падения" программы (segfault), если передали `nullptr`.
- [x] Zero-overhead Ownership: При передаче `shared_ptr` в конструктор и сеттер необходимо передавать их по значению и использовать `std::move` для присвоения полям класса, чтобы избежать лишних атомарных инкрементов/декрементов счетчика ссылок.

- Стандарт языка: C++17.
- Среда разработки и компилятор: Visual Studio (MSVC) / GCC 9+ / Clang 7+.
- Требования к коду: Строгое управление владением ресурсами (Zero-overhead ownership) с помощью `std::shared_ptr` и семантики перемещения (`std::move`) при смене стратегий. Обязательная валидация указателей перед разыменованием для предотвращения undefined behavior. Использование `override` для контроля полиморфных связей компилятором.
- Архитектурный паттерн: Dependency Inversion Principle в комбинации с поведенческим паттерном Strategy (Стратегия). Использование Constructor Injection (для начальной инициализации) и Setter Injection (для подмены зависимости в Runtime).
#### Логическая структура и взаимодействие классов:
Архитектура проекта демонстрирует динамическую гибкость, достигаемую за счет полного отделения контекста (ядра) от алгоритмов его работы.
- Уровень Бизнес-Логики (`namespace BusinessLogic`):
    - `IPaymentMethod` (Абстракция / Стратегия): Чистый виртуальный интерфейс, определяющий единый контракт для всех способов оплаты. Физически принадлежит ядру.
    - `OrderCheckout` (Ядро / Контекст): Класс оформления заказа. Делегирует ответственность за проведение платежа объекту, реализующему `IPaymentMethod`. Предоставляет интерфейс (`change_payment_method`) для безопасной "горячей" замены алгоритма оплаты прямо во время жизненного цикла объекта.
- Уровень Платежных шлюзов (`namespace PaymentGateways`):
    - `CreditCardPayment`: Конкретная реализация (стратегия) алгоритма оплаты через банковскую карту. Зависит от абстракции `IPaymentMethod`.
    - `CryptoPayment`: Альтернативная реализация (стратегия) алгоритма оплаты через криптовалюту. Легко добавляется в систему, не требуя модификации класса `OrderCheckout` (соблюдение Open/Closed Principle).
- Точка сборки (Composition Root):
    - `main.cpp`: Единственное место, где принимается решение о том, _как именно_ будет производиться оплата. Демонстрирует внедрение изначальной стратегии в ядро, выполнение бизнес-сценария, а затем динамическую подмену контекста и повторное выполнение операции с новым поведением.
#### Пример работы программы:

## Итог
Проделанный цикл из трех лабораторных работ позволил на практике закрепить принцип инверсии зависимостей (DIP) — фундаментальный столп современной программной архитектуры. Мы прошли путь от базовой изоляции слоев (DI) и защиты ядра от legacy-библиотек (Adapter) до создания систем с динамически изменяемым поведением (Strategy). Использование современных стандартов C++17, умных указателей и строгих пространств имен гарантирует, что спроектированный код не только гибок и масштабируем, но и абсолютно безопасен с точки зрения управления памятью, что полностью соответствует строгим требованиям коммерческой Senior-разработки.
