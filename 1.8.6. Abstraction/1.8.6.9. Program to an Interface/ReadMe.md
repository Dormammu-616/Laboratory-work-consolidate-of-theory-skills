## Лабораторная работа №1: «Разрыв зависимостей (Decoupling) и Инъекция зависимостей (DI)»
### ТЗ к лабораторной работе №1
**Цель работы:** Научиться устранять жесткое сцепление (tight coupling) между бизнес-логикой и инфраструктурным слоем. Освоить передачу абстракций через паттерн Dependency Injection (DI) с использованием Инъекции через конструктор (Constructor Injection).

#### 1. Архитектурные требования к контракту (Интерфейс)
Вам необходимо спроектировать интерфейс хранилища данных.
- **Название:** `IRepository`.
- **Правило абстракции:** Интерфейс должен описывать _роль_ (объект, который может сохранять данные), а не _детали_ (как именно он это делает).
- **Методы:** * Чисто виртуальный метод `saveOrder(std::string_view orderData)` (возвращает `bool` как статус успеха). Виртуальный деструктор по умолчанию.
- **Размещение:** Отдельный заголовочный файл `IRepository.hpp`.

#### 2. Разработка конкретных реализаций (Implementation)
Создайте два класса, которые будут реализовывать данный контракт, имитируя разное поведение.
- **`MySQLRepository`**:
    - Имитирует работу с базой данных.
    - В методе `saveOrder` должен выводить в консоль сообщение вида: `[MySQL] Подключение к БД... Заказ '...' сохранен успешно.`
- **`MemoryRepository`**:
    - Имитирует in-memory хранилище (полезно для быстрых тестов).
    - В методе `saveOrder` должен выводить в консоль: `[Memory] Заказ '...' сохранен в оперативной памяти.`

- **Зависимости:** Класс `OrderService` категорически не должен знать о существовании `MySQLRepository` или `MemoryRepository`. Он должен зависеть только от абстракции `IRepository`.
- **Инъекция (DI):** Используйте *Инъекцию через конструктор* — передавайте `std::shared_ptr<IRepository>` или ссылку `IRepository&` при создании объекта `OrderService`. Это самый явный и предпочтительный способ.

#### 4. Точка сборки (main.cpp)
В функции `main` продемонстрируйте гибкость архитектуры:
- Создайте экземпляр `MySQLRepository` и передайте его в `OrderService`. Вызовите `processNewOrder`.
- Создайте экземпляр `MemoryRepository` и передайте его в _новый_ или _тот же_ (если позволяет дизайн) `OrderService`. Вызовите `processNewOrder`.
- _Ожидаемый результат:_ Бизнес-логика отрабатывает идентично, но данные "улетают" в разные хранилища без единого изменения в коде самого `OrderService`.

## Лабораторная работа №2: «Расширение функциональности без модификации (Паттерн Decorator)»
### ТЗ к лабораторной работе №2
**Цель работы:** Научиться добавлять новую функциональность (например, логирование или кеширование) к существующим классам без изменения их исходного кода. Освоить паттерн Decorator, который позволяет элегантно расширять поведение объектов, оставаясь в рамках единого контракта.
#### 1. Проектирование бизнес-контракта (Интерфейс)
Создайте чистый интерфейс для обработки платежей.
- **Название:** `IPaymentProcessor`.
- **Методы:** Чисто виртуальный метод `processPayment(double amount)` (возвращает `bool` как статус успеха).
    - Виртуальный деструктор по умолчанию.
- **Размещение:** Отдельный заголовочный файл `IPaymentProcessor.hpp`.
#### 2. Базовая реализация (Concrete Component)
Создайте класс, который выполняет реальную "полезную" работу.
- **Название:** `StripePaymentProcessor`.
- **Поведение:** Наследует `IPaymentProcessor`. В методе `processPayment` он должен просто выводить в консоль сообщение: `[Stripe] Успешная транзакция на сумму: <amount> $` и возвращать `true`.
#### 3. Архитектурная магия: Декоратор (Decorator)
Здесь начинается самое интересное. Представьте, что к вам пришел менеджер и сказал: _"Нам нужно логировать каждый платеж в системе"_. Вместо того чтобы лезть в код `StripePaymentProcessor` и нарушать его работу, мы создадим обертку.
- **Название:** `LoggingPaymentProcessor`.
- **Наследование:** Он **тоже** должен наследовать `IPaymentProcessor`.
- **Состояние (Внедрение):** Внутри себя (в `private` области) он должен хранить умный указатель на обертываемый объект: `std::shared_ptr<IPaymentProcessor> m_wrappee`.
- **Конструктор:** Принимает этот `shared_ptr` и сохраняет его.
- **Поведение метода `processPayment`:** 1. Сначала выводит лог: `[Log] Начинаем обработку платежа на сумму <amount>...` 2. Затем **делегирует** работу реальному объекту: вызывает `m_wrappee->processPayment(amount)` и сохраняет результат в переменную. 3. Выводит лог: `[Log] Платеж завершен. Статус: <результат>` 4. Возвращает статус вызывающему коду.
#### 4. Изолированный клиентский код (StoreCheckout)
Создайте класс магазина, который ничего не знает о декораторах.
- **Название:** `StoreCheckout`.
- **Зависимости:** Принимает `std::shared_ptr<IPaymentProcessor>` через конструктор.
- **Поведение:** Метод `checkoutCart(double total)` выводит `[StoreCheckout] Оплата корзины...`, а затем вызывает метод `processPayment` у переданного процессора.
#### 5. Точка сборки (main.cpp)
Продемонстрируйте гибкость паттерна в функции `main`:
1. Создайте базовый объект `StripePaymentProcessor`.
2. Создайте объект `LoggingPaymentProcessor`, передав в его конструктор объект Stripe.
3. Передайте именно `LoggingPaymentProcessor` (обертку) в `StoreCheckout`.
4. Вызовите оплату корзины.
#### 📋 Критерии приемки (Checklist 2026)
- [x] Клиентский класс (`StoreCheckout`) абсолютно не догадывается, что работает с оберткой. Для него это всё тот же контракт `IPaymentProcessor`.
- [x] Достигнуто расширение поведения (добавлено логирование) без изменения единой строчки кода в базовом классе `StripePaymentProcessor`.
- [x] Максимальный уровень предупреждений компилятора (`/W4` и `/Wall`) проходит без ошибок.

### Документация к лабораторной работе №2
#### 3.1. Требования и стек технологий
- **Стандарт языка:** C++17.
- **Управление памятью:** Использование `std::shared_ptr` для управления жизненным циклом базовых объектов и их оберток. Оптимизация передачи владения через `std::move` для предотвращения лишнего копирования атомарных счетчиков ссылок.
- **Архитектурный стандарт:** Строгое соблюдение принципа Open/Closed Principle (OCP). Расширение поведения системы должно происходить без изменения исходного кода существующих классов.
#### 3.2. Логическая структура и взаимодействие классов.
Проект демонстрирует применение структурного паттерна _Decorator (Декоратор)_, который заменяет жесткое наследование гибкой композицией на уровне интерфейсов.
- **Контракты (Interfaces):**
    - `IPaymentProcessor.hpp` — единый абстрактный контракт для всех платежных систем и их потенциальных оберток. Описывает метод `process_payment(const double amount)`.
- **Базовая реализация (Concrete Component):**
    - `StripePaymentProcessor` — класс, выполняющий реальную, полезную бизнес-логику (имитацию проведения платежа через шлюз Stripe). Не содержит никакой сторонней логики (например, логирования).    
- **Декоратор (Decorator / Wrapper):**
    - `LoggingPaymentProcessor` — класс-обертка, реализующий архитектурную "магию". Он **наследует** `IPaymentProcessor` и одновременно **агрегирует** его внутри себя (хранит `std::shared_ptr<IPaymentProcessor>`). Перехватывает вызовы от клиента, добавляет этап логирования (до и после), а саму бизнес-логику _делегирует_ вложенному объекту. Для клиентского кода обертка абсолютно прозрачна: она честно возвращает статус, полученный от реального процессора.
- **Клиентский код (Client):**
    - `StoreCheckout` — класс магазина, принимающий интерфейс процессора через конструктор. Благодаря полиморфизму, класс не догадывается, что работает с оберткой-логгером, считая её обычным платежным шлюзом.
- **Точка сборки (Composition Root):**
    - `main.cpp` — выстраивает "матрешку" зависимостей: создает `StripePaymentProcessor`, помещает его внутрь `LoggingPaymentProcessor`, а затем передает этот декорированный объект в `StoreCheckout`.
#### 3.3. Пример работы программы
```cpp

[Log] Starting to process a payment to '47.5'$.
[Stripe] Successful transaction for the amount of '47.5$.'
[Log] Payment completed. Status: 'true'.
[StoreCheckout] Status payment: 'true'.
```

## Лабораторная работа №3: «Паттерн Стратегия (Strategy) — Динамическая смена алгоритмов»
### ТЗ к лабораторной работе №3
**Цель работы:** Понять разницу между статической привязкой алгоритма и динамической. Научиться изменять поведение объекта прямо во время выполнения программы (в Runtime), подменяя реализации единого интерфейса.
#### 1. Бизнес-контракт (Интерфейс)
Представьте, что мы пишем аналитическую систему, которая должна уметь выгружать отчеты в разных форматах.
- **Название:** `IExportStrategy`.
- **Методы:**
	- Чисто виртуальный метод `export_data(std::string_view report_data) const` (ничего не возвращает). *Обрати внимание на `const`, так как стратегия не должна менять свое внутреннее состояние при экспорте.*
    - Виртуальный деструктор по умолчанию.
#### 2. Конкретные стратегии (Concrete Strategies)
Создайте два класса, реализующих алгоритмы выгрузки:
- **`JsonExportStrategy`**:
    - Наследует `IExportStrategy`.
    - В методе `export_data` выводит: `[JSON Export] Выгрузка данных: { "data": "<report_data>" }`.
- **`CsvExportStrategy`**:
    - Наследует `IExportStrategy`.
    - В методе `export_data` выводит: `[CSV Export] Выгрузка данных: data;<report_data>`.
#### 3. Класс Контекста (Context)
Это класс, который будет использовать стратегию, но, в отличие от предыдущих лабораторных, он должен уметь **менять** её на лету.
- **Название:** `ReportManager`.
- **Состояние:** Хранит умный указатель `std::shared_ptr<IExportStrategy> m_strategy`.
- **Конструктор:** Принимает стартовую стратегию через `std::shared_ptr<IExportStrategy>`.
- **Метод `set_strategy`:** Принимает новый `std::shared_ptr<IExportStrategy>` и заменяет текущий указатель `m_strategy`. Это ключевой метод паттерна!
- **Метод `generate_report(std::string_view data)`:**
	1. Проверяет, установлена ли стратегия (например, `if (!m_strategy)`). Если нет, выводит предупреждение и выходит.
	2. Если установлена — выводит `[ReportManager] Подготовка отчета...` и вызывает метод `export_data` у текущей стратегии.
#### 4. Точка сборки (main.cpp)
Продемонстрируйте динамическую смену поведения:
1. Создайте экземпляр `JsonExportStrategy` и экземпляр `CsvExportStrategy`.
2. Создайте `ReportManager`, передав в него **JSON-стратегию**.
3. Вызовите `generate_report("Финансовый отчет за Май")`.
4. **Важный момент:** Прямо в `main` вызовите у `ReportManager` метод `set_strategy`, передав туда **CSV-стратегию**.
5. Снова вызовите `generate_report("Финансовый отчет за Июнь")` _у того же самого объекта_ `ReportManager`.

Проделанный цикл лабораторных работ позволил на практике закрепить один из важнейших принципов современной программной архитектуры — проектирование через абстрактные контракты, а не жестко связанные реализации. Применение паттернов Dependency Injection, Decorator и Strategy доказало, что инверсия зависимостей делает код невероятно гибким, открытым для расширения (OCP) и устойчивым к изменениям инфраструктуры. Использование современных возможностей C++17, семантики перемещения и строгих стандартов управления памятью гарантирует безопасность и эффективность созданных систем, что полностью соответствует требованиям коммерческой разработки (Production-ready).
