Данный цикл из трех лабораторных работ посвящен глубокому практическому освоению Принципа разделения интерфейса (Interface Segregation Principle — ISP), пятого столпа SOLID. В рамках проекта мы научимся выявлять архитектурные "запахи" (code smells) в виде "толстых" интерфейсов и рефакторить их в набор узкоспециализированных абстрактных контрактов (Role Interfaces). Представленный код на стандарте C++17 наглядно демонстрирует, как использование множественного наследования чистых интерфейсов избавляет классы от необходимости реализовывать ненужные методы и защищает систему от каскадных изменений.
## Лабораторная работа №1: Декомпозиция "толстого" интерфейса и ролевое проектирование (Decomposing a fat interface)

Изначальный монолитный контракт `ISmartDevice` привел к тому, что простые принтеры вынуждены содержать методы-заглушки для сканирования и отправки факсов.

## Лабораторная работа №2: Изоляция Legacy-кода через паттерн Адаптер (Isolating via the Adapter Pattern)
### Техническое задание
#### 1. Название, Контекст и Цель работы`
- *Название*: Изоляция Legacy-кода: применение паттерна Объектный Адаптер (Object Adapter) для соблюдения ISP.
- *Условный контекст*: В твой современный логистический проект внедряют старую библиотеку управления промышленными роботами. Сторонняя библиотека предоставляет гигантский, монолитный контракт `IUniversalRobotAPI` (умеет сваривать, красить, резать и перемещать). Твоя новая система логистики ожидает только робота-грузчика (узкий чистый контракт `IMover`). Изменять чужую библиотеку категорически запрещено (Legacy).
- *Цель работы*:
    - _Учебная:_ Закрепить навыки работы с композицией (Composition) как альтернативой множественному наследованию.
    - _Практическая:_ Научиться использовать структурный паттерн "Адаптер" (Object Adapter) для приведения "грязного" толстого интерфейса к чистому ролевому контракту без изменения исходного кода библиотеки.
#### 2. Архитектурные требования (Контракты и Абстракции)`
- Ролевой контракт твоей системы: Создай чистый интерфейс `IMover.hpp`.
    - Метод: `virtual void move_cargo(std::string_view destination) = 0;`
    - Обязательно: `virtual ~IMover() = default;`
- Контракт чужой библиотеки (Legacy): Создай файл `IUniversalRobotAPI.hpp`.
    - Методы (имитация "толстого" интерфейса): `virtual void weld() = 0;` `virtual void paint() = 0;` `virtual void carry_item(std::string_view target) = 0;`
    - Обязательно: `virtual ~IUniversalRobotAPI() = default;``
#### 3. Детали реализации (Конкретные компоненты)`
- Реализация чужого робота (`LegacyRobot`):
    - Наследует `IUniversalRobotAPI`.
    - Реализует все его методы (просто вывод в консоль, например `[LegacyRobot] Welding metal...` и `[LegacyRobot] Carrying item to: [target]`).
- Адаптер (`RobotMoverAdapter`):
    - Наследование: Наследует исключительно твой чистый интерфейс `IMover`.
    - Состояние (Композиция): Содержит ссылку на чужого робота `IUniversalRobotAPI& legacy_robot;`. Ссылка должна инициализироваться через конструктор адаптера.
    - Поведение: В переопределенном методе `move_cargo(destination)` адаптер выступает как переводчик — он просто делегирует работу легаси-роботу, вызывая внутри себя `legacy_robot.carry_item(destination)`.
#### 4. Изолированная бизнес-логика`
- Название: `LogisticsSystem.hpp` / `.cpp`
- Поведение: Класс системы должен иметь метод `void route_shipment(IMover& mover, std::string_view destination)`. Метод выводит лог `[LogisticsSystem] Routing shipment...` и вызывает `mover.move_cargo(destination)`. Система **ничего** не должна знать про существование `IUniversalRobotAPI`.`
#### 5. Точка сборки (main.cpp)** В функции `main`:
- Создай объект старого робота `LegacyRobot old_robot{};`.
- Создай объект адаптера `RobotMoverAdapter adapter{old_robot};`, передав ему старого робота.
- Создай систему логистики `LogisticsSystem system{};`.
- Передай адаптер в систему: `system.route_shipment(adapter, "Warehouse A");`.
- *Суть архитектуры*: Убедись, что "толстый" робот успешно работает в системе логистики, которая требует узкий интерфейс, при этом сам робот остался нетронутым.`
#### 6. Критерии профессионального выполнения
- [x] Паттерн реализован строго через композицию (Object Adapter), а не через приватное наследование (Class Adapter). Адаптер хранит ссылку на адаптируемый интерфейс.
- [x] Адаптер запрещено копировать (non-copyable семантика через `= delete`), так как он управляет "подключением" к физическому устройству.
- [x] Полное отсутствие предупреждений компилятора (`/W4` или `-Wall`).

## Лабораторная работа №3: Клиент-ориентированные интерфейсы в сложных системах ()
### Техническое задание
#### 1. Название, Контекст и Цель работы
- *Название*: Архитектурная декомпозиция: проектирование клиент-ориентированных интерфейсов (Multiple Role Interfaces).
- *Условный контекст*: Вы разрабатываете систему управления облачным кластером. В дата-центре есть сложный узел — `CloudServer` (Облачный сервер). С этим сервером работают три совершенно независимые системы (клиенты):

    2. Система телеметрии (собирает метрики нагрузки: CPU, RAM).
    3. Панель администратора (может жестко перезагрузить сервер). Если мы отдадим всем трем клиентам один интерфейс `IServer`, то изменение логики перезагрузки заставит нас перекомпилировать систему телеметрии, что недопустимо в архитектуре уровня Enterprise.
- *Цель работы*:
    - _Учебная:_ Освоить концепцию "Client-Specific Interfaces", когда архитектура диктуется не тем, _что умеет_ класс, а тем, _что от него требуют_ конкретные клиенты.
    - _Практическая:_ Написать сложный класс, который через множественное наследование реализует набор независимых чистых контрактов, и гарантировать строгую изоляцию (каждый клиент видит только свою часть функционала).

    - `virtual ~IRebootable() = default;`
#### 3. Детали реализации (Конкретные компоненты)

2. Создайте экземпляры всех трех клиентов: `TaskScheduler`, `TelemetryDashboard`, `AdminConsole`.
3. Передайте *один и тот же объект `CloudServer`* по очереди в каждый из трех клиентов.
4. _Суть архитектуры:_ Вы своими глазами увидите (и докажете компилятором), как один сложный "божественный" объект изящно распадается на три разные роли, и ни один клиент не может случайно вызвать метод, не относящийся к его зоне ответственности (например, телеметрия физически не сможет вызвать `reboot`, хотя работает с тем же самым сервером).
#### 6. Критерии профессионального выполнения
- [x] Глубокое понимание Const Correctness (правильное использование `const` для чтения метрик на всех уровнях архитектуры).
- [x] Явный запрет копирования инфраструктурного объекта (`CloudServer`).
- [x] 100% покрытие атрибутом `[[nodiscard]]` методов, возвращающих значения.
- [x] Идеально чистая компиляция с флагами `/W4` или `-Wall`.

### Документация
#### Требования и стек технологий:
- *Стандарт языка:* ISO C++17. Активно используются атрибут `[[nodiscard]]` для контроля возвращаемых значений, `std::string_view` для оптимизации передачи строк, а также строгая семантика запрета копирования (`= delete`).
- *Компилятор:* MSVC (Microsoft Visual C++), GCC 7+ или Clang 5+ (с полной поддержкой C++17).
- *Флаги компиляции:* Максимально строгий режим (`/W4` или `-Wall`). Это критически важно для проверки Const Correctness (константной корректности) и отлова игнорируемых `[[nodiscard]]` значений.
- *Среда разработки:* Visual Studio 2022 (или любая современная C++ IDE).
#### Логическая структура и взаимодействие классов:
Архитектура данной лабораторной работы демонстрирует концепцию «Client-Specific Interfaces» (Клиент-ориентированные интерфейсы) для сложных инфраструктурных объектов:
- *Ролевые контракты* (Интерфейсы):
    - `IComputeNode`, `IMonitorable`, `IRebootable` — три независимых, узких и чистых контракта, спроектированных не от возможностей сервера, а исключительно от потребностей конкретных систем (клиентов).
- *Конкретная реализация* (Инфраструктурный объект):
    - `CloudServer` — сложный физический узел, хранящий состояние (ID). Он использует множественное наследование интерфейсов, чтобы одновременно исполнять все три роли. Объект сделан строго Non-copyable, так как является уникальным системным ресурсом.
- *Изолированная бизнес-логика* (Клиенты):
    - `TaskScheduler`, `TelemetryDashboard`, `AdminConsole` — независимые потребители. Важнейшая архитектурная деталь: `TelemetryDashboard` принимает сервер по константной ссылке (`const IMonitorable&`), гарантируя защиту состояния сервера от изменений при сборе метрик (Const Correctness).
- *Взаимодействие* (Точка сборки):
    - В `main.cpp` создается ровно один физический объект `CloudServer`. Этот единый объект передается трем разным системам-клиентам. Благодаря строгой типизации, каждая система "видит" только разрешенную ей часть контракта (маску), что делает невозможным вызов деструктивных команд (например, перезагрузки) из модулей мониторинга.
#### Пример работы программы:
```cpp
[TaskScheduler] Distribution of work 'read data'.
[CloudServer] Completing the task 'read data'.
[TelemetryDashboard] Collecting data...
[CloudServer] Sending metrics: server id 'simple-server'.
        result: simple-server.
[AdminConsole] Restarting the server...
[CloudServer] Reboot...
```

## Итог
Проделанный цикл из трех лабораторных работ позволил на глубоком практическом уровне освоить Interface Segregation Principle (Принцип разделения интерфейса) — важнейший инструмент проектирования отказоустойчивых систем.
В ходе работы *были отработаны ключевые паттерны и архитектурные приемы*:
1. *Декомпозиция монолитов:* Успешный уход от "толстых" интерфейсов (Fat Interfaces) в пользу узких ролевых контрактов (Role Interfaces), исключающих наличие методов-заглушек.
2. *Изоляция Legacy-кода:* Применение структурного паттерна Object Adapter (Адаптер объекта) доказало свою эффективность при внедрении "грязных", перегруженных сторонних библиотек в чистую бизнес-логику без нарушения правил инверсии зависимостей.
3. *Клиент-ориентированное проектирование:* Реализация сложных инфраструктурных объектов, предоставляющих разным клиентам строго ограниченные "пульты управления" с соблюдением Const Correctness и защитой от копирования.
Главным архитектурным достижением этого цикла стал перенос потенциальных логических ошибок из времени выполнения (Runtime Error) на этап компиляции (Compile-time Error). Проектирование, отталкивающееся от потребностей клиента, а не от реализации, делает код на C++ невероятно надежным, безопасным, легко масштабируемым и полностью готовым к стандартам коммерческой Enterprise-разработки.
