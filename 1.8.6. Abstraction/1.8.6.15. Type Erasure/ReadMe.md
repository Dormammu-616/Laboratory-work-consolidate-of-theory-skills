Этот цикл из трех лабораторных работ посвящен практическому освоению мощного архитектурного паттерна «Стирание типа» (Type Erasure) в современном стандарте C++17. В ходе практики мы пройдем путь от проектирования базовой неинвазивной обертки на основе идиомы _Concept/Model_ до реализации полноценного гетерогенного контейнера с поддержкой глубокого копирования и безопасной семантики значения. Итогом станет создание собственного высокопроизводительного инфраструктурного инструмента, готового к использованию на изолированных границах сложных Enterprise-систем без нарушения ABI.
## Лабораторная работа №1: Базовая идиома Concept/Model и неинвазивный полиморфизм (Basic Concept/Model Idiom)
### Техническое задание
#### Контекст и цель работы
- *Условный контекст:* Ты разрабатываешь графическую подсистему для нового игрового движка (Render Pipeline). Исторически в движке нет единого базового класса для графических примитивов. Более того, недавно была куплена проприетарная сторонняя библиотека высокополигональных моделей (Mesh), исходный код которой закрыт для модификации. Тебе необходимо создать единую очередь рендеринга для всех этих разрозненных объектов.
- *Учебная цель:* Закрепить идиому Concept/Model, осознать процесс "захвата типа" (Type Capture) в конструкторе и научиться использовать динамическую диспетчеризацию через виртуальные методы внутри скрытых классов-моделей.
- *Практическая цель:* Реализовать очередь рендеринга (`vector<AnyRenderable>`), которая позволяет обрабатывать разнородные примитивы единообразно без изменения их исходного кода. Цель — заставить объекты совершенно разных, не связанных друг с другом типов (включая сторонние), лежать в одном стандартном массиве и полиморфно обрабатываться в цикле без использования паттерна "Адаптер" и без единого публичного базового интерфейса.
#### Архитектурные требования (Контракты и Абстракции)
Необходимо спроектировать главный класс-фасад — Обертку `AnyRenderable`. Этот класс должен быть реализован строго по идиоме _Concept/Model_:
- Внутри `AnyRenderable` в приватной секции объяви чисто виртуальную структуру `Concept` с методом `do_render() const = 0` и обязательным виртуальным деструктором.
- Там же, в приватной секции, создай шаблонную структуру `Model<T>`, которая финально (`final`) наследуется от `Concept`. Она должна хранить объект типа `T` по значению и переопределять `do_render() const`, вызывая внутри специфичный метод `render()` у сохраненного объекта (реализация утиной типизации времени компиляции).
- Сам фасад `AnyRenderable` должен содержать единственное поле данных: `std::unique_ptr<Concept>`.
- Фасад должен иметь шаблонный конструктор для "захвата" любого типа `T` и публичный метод `render() const`, который перенаправляет вызов внутреннему указателю.
- _Ограничение первой лабы:_ Так как `unique_ptr` не копируется, наша обертка пока будет Move-Only (только для перемещения). Отключи конструктор копирования и оператор присваивания, но разреши перемещение (`'= default`).
#### Детали реализации (Конкретные компоненты)
Создать три совершенно независимых класса. Никакого наследования!
- Класс `Circle` с методом `void render() const`, который выводит в консоль `"Rendering Circle"`.
- Класс `Square` с методом `void render() const`, который выводит `"Rendering Square"`.
- Пространство имен `ThirdParty`, внутри которого находится класс `OptimizedMesh` с методом `void render() const`, выводящим `"Rendering highly optimized Third-Party Mesh"`.
#### Изолированная бизнес-логика
- Создай класс `RenderPipeline`.
- У него должен быть метод `add_renderable(AnyRenderable&& object)`, который принимает обертку (по r-value ссылке) и кладет её во внутренний контейнер `std::vector<AnyRenderable> queue_`.
- Метод `execute_frame() const`, который итерируется по `queue_` и вызывает метод `render()` у каждого элемента.
#### Точка сборки (`main.cpp`)

- Создай объекты `Circle`, `Square` и `ThirdParty::OptimizedMesh`.
- Помести их все в пайплайн. Обрати внимание, что из-за Move-Only семантики Обертки, объекты нужно передавать через `std::move` или конструировать на месте (r-value).

#### Критерии профессионального выполнения
- [x] В коде полностью отсутствует ключевое слово `virtual` вне класса `AnyRenderable` (наши примитивы — обычные легковесные классы).
- [x] Жесткое соблюдение _Const Correctness_ (все методы рендеринга должны быть `const`).
- [x] Отсутствие утечек памяти: правильное удаление обеспечивается виртуальным деструктором внутри `Concept` и автоматикой `std::unique_ptr`.
- [x] Код компилируется со стандартом C++17 без единого предупреждения (флаги `/W4` в MSVC или `-Wall -Wextra` в GCC/Clang).

- **Бизнес-логика — `RenderPipeline`:** Оркестратор. Владеет гетерогенным контейнером `std::vector<AnyRenderable>` и в цикле полиморфно отрисовывает совершенно разнородные объекты (`Circle`, `Square`, `ThirdParty:OptimizedMesh`), ничего не зная об их реальных типах.

## Лабораторная работа №2: Семантика значения и глубокое копирование (Type Erasure-Value Semantics)
### Техническое задание
#### Контекст и Цель работы
- *Условный контекст:* Ты разрабатываешь физический движок для космического симулятора (Sci-Fi Sandbox). Игровой мир состоит из совершенно разных объектов: астероидов, космических кораблей и черных дыр из закрытого стороннего физического плагина. Геймдизайнерам потребовался инструмент "Клонирующей пушки" (Clone Gun), который позволяет скопировать любой участок космоса или размножить скопление астероидов.
- *Учебная цель:* Закрепить реализацию структурного паттерна «Прототип» (Prototype) внутри скрытой архитектуры, освоить «Правило Пяти» (Rule of Five) и реализовать строгую гарантию безопасности исключений через идиому Copy-and-Swap.
- *Практическая цель:* Разработать гетерогенную обертку-значение (Value Type), которую можно безопасно копировать. Копирование должно приводить к созданию независимого клона в динамической памяти, исключая проблему разделяемого состояния (Shared State).
#### Архитектурные требования (Контракты и Абстракции)
Спроектируй новый класс-фасад `AnySimulatable`:
- Концепт (`Concept`): Должен содержать виртуальный метод `simulate() const = 0` и новый чисто виртуальный метод `clone() const = 0`, который возвращает `std::unique_ptr<Concept>`.
- Модель (`Model<T>`): Реализует `simulate() const` (вызывая метод реального объекта). Также реализует `clone() const`, где с помощью `std::make_unique<Model<T>>(*this)` происходит физическое глубокое копирование сохраненного значения `T` и возврат нового умного указателя.
- Правило Пяти в `AnySimulatable`:
    1. _Шаблонный конструктор_ (для захвата типа).
    2. _Конструктор копирования_ — проверяет, не пустой ли `pimpl_` у другого объекта, и вызывает у него `clone()`.
    3. _Оператор копирующего присваивания_ (`operator=`) — реализован строго через передачу по значению и метод `swap` (Copy-and-Swap idiom). Должен быть помечен `noexcept`.
    4. _Конструктор перемещения_ (`'= default'` или `noexcept` с перемещением указателя).
    5. _Деструктор_ (`'= default'`).
#### Детали реализации (Конкретные компоненты)
Создай три класса в `SpaceObjects.hpp` (без базового класса):
- Класс `Asteroid`: Содержит поле `mass_` (тип `int64_t`). Метод `void simulate() const`. Вывод: `"[Asteroid] Mass: <mass>, Address: <адрес this>"`.
- Класс `Starship`: Содержит поле `name_` (тип `string`). Метод `void simulate() const`. Вывод: `"[Starship] Name: <name>, Address: <адрес this>"`.
- Пространство имен `ThirdParty`: Внутри класс `BlackHole`. Метод `void simulate() const`. Вывод: `"[ThirdParty:BlackHole] Consuming light, Address: <адрес this>"`.
Архитектурное примечание: Использование единого имени метода `simulate()` во всех классах реализует принцип **статического полиморфизма (Compile-time Polymorphism)**, который позволяет обертке `AnySimulatable` единообразно вызывать методы разных типов без использования интерфейсов.
#### Изолированная бизнес-логика
Спроектируй класс `SimulationGrid`:
- Хранит `std::vector<AnySimulatable> grid_`.
- Метод `void add_entity(AnySimulatable entity)` (принимает по значению!).
- Новый метод: `void duplicate_entity(size_t index)`. Этот метод должен взять объект по индексу из `grid_` и сделать `grid_.push_back(grid_[index]);`. (Здесь сработает твой конструктор копирования!)
- Метод `void run_tick() const`, который итерируется по вектору и вызывает метод симуляции у Обертки.
#### Точка сборки (`main.cpp`)
- Создай `SimulationGrid`.
- Создай объекты `Asteroid(5000)`, `Starship("Millennium Falcon")`, `ThirdParty::BlackHole()`.
- Добавь их в `SimulationGrid`.
- Вызови `duplicate_entity(0)` (склонируй астероид).
- Вызови `duplicate_entity(1)` (склонируй корабль).
- Вызови `run_tick()`.
- *Доказательство*: В консоли ты должен увидеть 5 объектов. У оригинального астероида и его клона массы будут одинаковыми (5000), но адреса памяти (this) обязаны быть разными. То же самое для кораблей.
#### Критерии профессионального выполнения
- [x] Инкапсуляция семантики: Класс `AnySimulatable` корректно ведет себя как Value Type (тип-значение): объекты можно копировать, присваивать и безопасно хранить в контейнерах.
- [x] Идиома Copy-and-Swap: Оператор присваивания `operator=` реализован через передачу аргумента по значению и метод `swap`, обеспечивая строгую гарантию безопасности (Strong Exception Guarantee) и отсутствие утечек.
- [x] Изоляция типов: Глубокое копирование реализовано через виртуальный метод `clone()`, позволяющий создавать копии объектов без знания их конкретного типа (Concrete Type) во время компиляции.
- [x] Стабильность ABI: Использование `std::unique_ptr` и pimpl-идиомы внутри фасада обеспечивает независимость клиентского кода от изменений в структуре данных (Model).

## Лабораторная работа №3: Стирание типа с мутацией состояния и возвратом значений (State mutation and return values)
### Техническое задание
#### Контекст и Цель работы
- *Условный контекст:* Ты разрабатываешь высоконагруженный серверный планировщик фоновых задач (Background Job Scheduler) для крупной e-commerce платформы. В очередь планировщика поступают абсолютно разные задачи от разных команд: очистка базы данных, отправка писем клиентам, генерация отчетов из легаси-плагинов. Каждая задача при выполнении может изменять свое состояние (например, счетчик обработанных записей) и должна сообщать планировщику об успехе или провале своей работы (возвращать `bool`).
- *Учебная цель*: Настроить паттерн Type Erasure на работу с неконстантными (`non-const`) методами, освоить возврат значений из стертых типов и закрепить «Правило Пяти» (глубокое копирование).
- *Практическая цель*: Создать гетерогенную очередь команд (`Command Pattern` на стероидах), где команды могут изменять собственные данные при каждом вызове, а планировщик может реагировать на статус выполнения задачи.
#### Архитектурные требования (Контракты и Абстракции)
Спроектируй класс `AnyJob`:
- Концепт (`Concept`): Имеет виртуальный деструктор. Содержит чисто виртуальный метод `bool execute() = 0;` (Обрати внимание: без `const`! Мы будем менять состояние объектов). Также содержит метод `std::unique_ptr<Concept> clone() const = 0;` (копирование константно, оно не меняет оригинал).
- Модель (`Model<T>`): Реализует `execute()`, вызывая неконстантный метод `execute` у сохраненного `T`, и возвращает его результат. Также реализует `clone()`.
- Правило Пяти в `AnyJob`:
	- Нешаблонный конструктор копирования (через `clone`).
    - Оператор `operator=` через идиому _Copy-and-Swap_.
    - Конструктор перемещения (`'= default'`).
    - Шаблонный конструктор (захват по значению `T obj`, как мы делали во второй лабе).
    - Публичный бизнес-метод `bool execute()`.
#### Детали реализации (Конкретные компоненты)
Создай три класса в `BackgroundTasks.hpp` (без общего предка):
- Класс `DatabaseCleanup`: Содержит приватное поле `int tables_cleaned_{0}`. Метод `bool execute()`. При вызове увеличивает счетчик на 10 и выводит: `"[DatabaseCleanup] Tables cleaned so far: <счетчик>"`. Возвращает `true`.
- Класс `EmailNotification`: Принимает в конструкторе `std::string recipient`. Метод `bool execute()`. Выводит: `"[EmailNotification] Sending email to <recipient>..."`. Возвращает `true`.
- Пространство имен `Legacy`, класс `ReportGenerator`: Метод `bool execute()`. Выводит: `"[Legacy:ReportGenerator] CRITICAL ERROR: Server unreachable!"`. Возвращает `false`.
#### Изолированная бизнес-логика
Спроектируй класс `JobScheduler`:
- Хранит очередь задач: `std::vector<AnyJob> queue_`.
- Метод `void schedule(AnyJob job)` (принимает по значению, чтобы можно было безопасно копировать или перемещать объекты внутрь вектора).
- Метод `void run_all()`. Этот метод должен итерироваться по `queue_` (обрати внимание, итератор должен позволять изменение объекта, то есть `auto&`, а не `const auto&`). Для каждой задачи он вызывает `execute()`. Если метод возвращает `false`, планировщик должен вывести в консоль дополнительное сообщение: `"[JobScheduler] Warning: A job has failed!"`.
#### Точка сборки (`main.cpp`)

- Создай `DatabaseCleanup`, `EmailNotification` и `Legacy::ReportGenerator`.

- Добавь в расписание остальные задачи.
- Вызови `run_all()` у планировщика.
- *Секретная проверка мутации:* После первого вызова `run_all()`, вызови `run_all()` еще раз! В консоли ты должен увидеть, что счетчик у `DatabaseCleanup` увеличился (в первый проход было 10, во второй проход должно стать 20), что докажет: состояние объектов внутри `AnyJob` успешно мутирует.
#### Критерии профессионального выполнения
- [x] Жесткий контроль константности: `execute()` обязаны быть неконстантными (и в `AnyJob`, и в `Concept`, и в `Model`, и в самих задачах), а `clone()` обязан остаться `const`.
- [x] Отсутствие предупреждений компилятора (`/W4`).
- [x] Никакого наследования между классами задач.
- [x] Полное отсутствие утечек (используем только `unique_ptr`).
### Документация
#### Требования и стек технологий:
- Стандарт языка: C++17.
- Компилятор: Совместимый с C++17 (MSVC, GCC, Clang).
- Система сборки: CMake (версия 3.10+).
- Флаги компиляции: Строгий уровень предупреждений (`/W4` или `-Wall -Wextra`).
#### Логическая структура и взаимодействие классов:
Архитектура представляет собой продвинутую реализацию паттерна "Команда" без использования классического наследования от базового интерфейса `ICommand`.
- *Фасад (`AnyJob`):* Тип-значение (Value Type), скрывающий полиморфную логику. Предоставляет клиенту неконстантный метод `execute()` для мутации внутреннего состояния задачи и возврата статуса (`bool`). Управляет жизненным циклом (глубокое копирование через `clone()`, перемещение, удаление).
- *Абстракция (`Concept` / `Model<T>`):* Внутренний механизм стирания типа. `Model<T>` инкапсулирует конкретный объект `T` по значению и транслирует вызовы. Поддерживает утиную типизацию (duck typing).
- *Конкретные задачи (`DatabaseCleanup`, `EmailNotification`, `Legacy:ReportGenerator`):* Полностью независимые классы. Не имеют общих предков, могут находиться в разных пространствах имен, но обязаны иметь публичный неконстантный метод `bool execute()`.
- *Оркестратор (`JobScheduler`):* Контейнер задач. Использует идиому Sink Parameter в методе `schedule(AnyJob job)`, позволяя компилятору максимально эффективно решать, когда применять копирование (Deep Copy), а когда перемещение (Move). При выполнении `run_all()` итерируется по мутируемым ссылкам и обрабатывает статус выполнения каждой задачи.

## Итог
Проделанный цикл из трех лабораторных работ позволил на глубоком архитектурном уровне освоить идиому Type Erasure (Стирание типа) — одну из самых мощных техник современного C++. Был пройден путь от создания простейшей `Move-Only` обертки (Concept/Model idiom) до полноценного полиморфного типа с семантикой значения (Value Semantics), поддержкой глубокого копирования (паттерн Prototype) и мутацией внутреннего состояния. Главным архитектурным достижением стала реализация "полиморфизма без наследования" (Duck Typing на этапе компиляции): система научилась объединять в стандартные контейнеры (`vector`) абсолютно разнородные классы из разных библиотек, не заставляя их наследоваться от единого интерфейса. Это обеспечивает феноменальную слабую связность (Loose Coupling), избавляет от проблем с висячими ссылками (управление памятью скрыто в фасаде) и делает код максимально гибким, безопасным и готовым к стандартам разработки высоконагруженных систем уровня Enterprise.
