В данной серии из трех лабораторных работ мы глубоко погрузимся в архитектурную идиому Non-Virtual Interface (NVI). Практика направлена на разделение двух обычно переплетенных ответственностей: определения стабильного интерфейса для клиентов и предоставления точек расширения для классов-наследников. Первая лабораторная работа посвящена классическому и самому строгому варианту NVI — использованию приватных виртуальных методов. Этот подход предоставляет базовому классу полный контроль над порядком выполнения операций, позволяя гарантировать соблюдение системных инвариантов и корректное управление ресурсами.
## Лабораторная работа №1: Гарантия инвариантов графической подсистемы с помощью NVI (Guaranteeing GUI invariants using NVI)
### Техническое задание
#### Контекст и Цель работы
- *Условный контекст*: Разработка графического движка для UI-фреймворка электромобиля. Базовый класс виджета должен гарантировать, что перед отрисовкой любого контента графический контекст корректно захватывается, а после — освобождается и логируется.
- *Цель работы*:
    - *Учебная*: Изучить и закрепить на практике шаблон создания публичной невиртуальной обертки, вызывающей приватный виртуальный метод.
    - *Практическая*: Полностью исключить риск утечки графического контекста из-за того, что разработчик конкретного виджета забыл вызвать базовую реализацию или нарушил порядок инициализации ресурсов.
#### Архитектурные требования (Контракты и Абстракции)
- Базовый абстрактный класс `Widget` должен содержать публичный невиртуальный метод `render()`, представляющий собой стабильный контракт для вызывающей стороны.
- Метод `render()` должен инкапсулировать логику предварительных проверок, выделения графического контекста, вызова точки расширения и финальной очистки.
- Точка расширения должна быть объявлена как `private virtual void drawContent() const = 0;`.
- Класс должен иметь виртуальный деструктор `virtual ~Widget() = default;`.
#### Детали реализации (Конкретные компоненты)
- Необходимо реализовать два конкретных класса: `ButtonWidget` и `TextWidget`.
- Каждый класс-наследник должен переопределить приватный метод `drawContent()` с обязательным использованием спецификатора `override`.
- Внутри переопределенного метода наследники должны выводить в консоль только логику специфичной отрисовки (например, "Drawing Button borders and text"), не обращаясь к инфраструктурным ресурсам напрямую.
#### Изолированная бизнес-логика (Взаимодействие компонентов)
- `UIEngine` (Менеджер отрисовки):
    - Реализовать свободную функцию (или статический метод класса-менеджера): `void renderUI(const std::vector<std::shared_ptr<Widget>>& widgets)`
    - _Суть компонента:_ Выступает в роли "клиента" для нашего контракта. Функция должна в цикле обойти все элементы вектора и вызвать для каждого метод `render()`. Она ничего не должна знать о внутреннем устройстве конкретных кнопок или текстов, а также не должна управлять памятью GPU напрямую — всё это инкапсулировано внутри базового `Widget`.
#### Точка сборки и сценарий проверки (main.cpp)
- Создать полиморфный контейнер: `std::vector<std::shared_ptr<Widget>> ui_elements;`.
- Инстанцировать конкретные виджеты через `std::make_shared<ButtonWidget>()` и `std::make_shared<TextWidget>()`, поместив их в контейнер.
- Передать подготовленный контейнер в бизнес-логику `renderUI`.
- _Цель этапа:_ Продемонстрировать полиморфное поведение через невиртуальный интерфейс (NVI). Убедиться, что инфраструктурный код базового класса стабильно выполняется _вокруг_ специфичной отрисовки каждого наследника, исключая возможность утечки ресурсов.

## Лабораторная работа №2: Расширение поведения по умолчанию через NVI с использованием `protected virtual` методов (Extending default behavior via NVI)
### Техническое задание
#### Контекст и Цель работы
- *Условный контекст:* Разработка модуля экспорта данных для корпоративной CRM-системы. Базовый алгоритм гарантирует правильное открытие и закрытие файловых потоков (имитация), а форматирование данных имеет базовую реализацию (сырой текст — Raw Text), которую можно переопределить для JSON или XML.
- *Цель работы:*
	- *Учебная:* Изучить отличия между `private virtual` (когда реализация строго обязательна) и `protected virtual` (когда базовый класс дает дефолтное поведение).
    - *Практическая*: Построить расширяемую систему плагинов экспорта, где создание нового, нестандартного экспортера не требует дублирования базового кода алгоритма.
#### Архитектурные требования (Контракты и Абстракции)
- Создать класс `DataExporter`. Он должен содержать публичный невиртуальный метод `export_data()`, который является шаблонным методом (Template Method).
- Метод `export_data()` должен имитировать открытие файла, вызывать точку расширения, а затем гарантированно имитировать закрытие файла.
- Точка расширения должна быть объявлена как **`protected virtual void format_data() const;`** (обрати внимание, здесь нет `= 0`, метод _не_ является чисто виртуальным).
- Базовый класс должен реализовать этот метод внутри `.cpp` файла (вывести в консоль `"[DataExporter] Formatting as Raw Text..."`).
- Класс обязан иметь виртуальный деструктор `virtual ~DataExporter() = default;`.
#### Детали реализации (Конкретные компоненты)

- `JsonExporter`: Наследуется от `DataExporter`. Переопределяет метод `format_data()` с ключевым словом `override`. Внутри выводит `"[JsonExporter] Formatting as JSON..."`.
- `XmlExporter`: Наследуется от `DataExporter`. Переопределяет метод `format_data()` с ключевым словом `override`. Внутри выводит `"[XmlExporter] Formatting as XML..."`.
#### Изолированная бизнес-логика

- Внутри реализовать свободную функцию `void process_exports(const std::vector<std::shared_ptr<DataExporter>>& exporters)`.
- Функция должна в цикле итерироваться по переданным экспортерам и вызывать публичный метод `export_data()`. Она ничего не знает о форматах, её задача — просто запустить процесс пакетной выгрузки.

- Создать контейнер `std::vector<std::shared_ptr<DataExporter>>`.
- Поместить в него экземпляры `RawExporter`, `JsonExporter` и `XmlExporter`.

## Лабораторная работа №3:  (Freezing NVI using the final specifier)
### Техническое задание
#### Контекст и Цель работы
- *Условный контекст*: Разработка ядра обработки сетевых запросов (Network Request Handler) для банковского шлюза. Базовый алгоритм гарантирует обязательное логирование начала и конца транзакции, а конкретные протоколы (HTTP, FTP) реализуют свою передачу данных. Из соображений безопасности логика конкретных протоколов не должна подлежать дальнейшему переопределению возможными наследниками.
- *Цель работы*:
	- *Учебная*: Освоить применение спецификатора `final` для виртуальных методов и классов в контексте идиомы NVI.
    - *Практическая*: Спроектировать защищенную архитектуру, в которой компилятор физически запретит дальнейшее изменение критически важной реализации в классах-потомках.
#### Архитектурные требования (Контракты и Абстракции)
- Создать базовый абстрактный класс `NetworkProcessor`.
- Он должен содержать публичный невиртуальный метод `process_request()`. Этот метод является стабильным контрактом: он имитирует открытие соединения, вызывает скрытую точку расширения и имитирует закрытие соединения.
- Точка расширения должна быть объявлена как `private virtual void handle_payload() const = 0;`.
- Виртуальный деструктор обязателен `virtual ~NetworkProcessor() = default;`.

    - _Логика:_ Выводит `"[HttpProcessor] Processing HTTP POST payload..."`.
- Класс `FtpProcessor`: Наследуется от `NetworkProcessor`.
    - Критическое требование: Сам класс должен быть помечен как `final` (`class FtpProcessor final : public NetworkProcessor`). Это альтернативный и более жесткий способ запретить наследование на уровне всего класса.
    - Переопределяет метод `handle_payload()` (с `override`).
    - _Логика:_ Выводит `"[FtpProcessor] Processing FTP file transfer..."`.
#### Изолированная бизнес-логика (Взаимодействие компонентов)

- Внутри реализовать свободную функцию `void run_network_pipeline(const std::vector<std::shared_ptr<NetworkProcessor>>& processors)`.

## Итог
Проделанный цикл из трех лабораторных работ позволил на глубоком уровне освоить идиому **Non-Virtual Interface (NVI)**. На первый взгляд, исходный код всех трех проектов может показаться практически идентичным: схожая структура классов, одинаковый паттерн `Template Method`, один и тот же принцип инкапсуляции.
Однако реальная разница между ними кроется в использовании буквально 1-2 ключевых слов современного C++ (`private = 0`, `protected`, `final`). В архитектурном проектировании мы управляем не только алгоритмами, но и **контрактами и ограничениями**. Для компилятора и для программиста, который будет расширять этот код в будущем, эти ключевые слова меняют правила игры фундаментально:
1. *Лабораторная №1 (`private virtual = 0`)* — Жесткий контракт: Базовый класс выступает диктатором алгоритма. Он не предоставляет поведения по умолчанию и обязывает наследника написать собственную реализацию (`draw_content`), иначе проект не скомпилируется. При этом прямое вмешательство в базовый процесс извне полностью исключено.
2. *Лабораторная №2 (`protected virtual`)* — Мягкий контракт (Опциональность): Базовый класс предоставляет дефолтное безопасное поведение (например, экспорт в Raw Text). Наследник имеет право выбора: взять готовую реализацию "бесплатно" (как `RawExporter`) или точечно кастомизировать ее под свои нужды (`JsonExporter`), не ломая общий алгоритм инициализации и очистки.
3. *Лабораторная №3 (`final`)* — Фиксация иерархии (Бетонная стена): Применение спецификатора `final` (на уровне метода или всего класса) позволяет "заморозить" критически важный алгоритм (например, HTTP или FTP обработчик). На уровне компилятора физически запрещается любое дальнейшее наследование и изменение логики, что гарантирует абсолютную безопасность ядра системы от непреднамеренных модификаций.
Использование идиомы NVI в связке с возможностями стандарта C++17 позволяет создавать невероятно надежные системы. Разделяя публичный контракт (что класс делает) и виртуальный интерфейс (как наследник это реализует), мы исключаем риск утечек ресурсов, забытых вызовов базовых методов и нарушений бизнес-логики. Спроектированный таким образом код полностью готов к требованиям коммерческой Enterprise-разработки.
